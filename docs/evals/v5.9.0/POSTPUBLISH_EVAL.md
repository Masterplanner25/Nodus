## The index lag, again

`pip install nodus-lang==5.9.0` failed immediately after a successful upload:

```
ERROR: No matching distribution found for nodus-lang==5.9.0
```

This is the documented behaviour, not a failed upload — the same lag hit 5.8.0,
and at 5.6.0 the JSON API reported *zero files* for a version that had just
landed. Retrying until it resolved is the whole remedy. **Only
`pip install <name>==<version>` is authoritative**; a JSON-API check at this
moment would have reported the previous release and read exactly like a failure.

## Every 5.9.0 claim, exercised on the published package

One program, run from a neutral directory against the installed wheel:

```
696 returned closure: 13
696 stateful: 1 2 3
170 round trip: [137, 80, 78, 71, 26, 255]
170 as text: io_error
691 into-module: 7
retry.until in step: 3
workflow failed: []
workflow steps: {"a": "ok"}
```

Line by line:

- **#696** — `m.make_adder(3i)(10i)` is `13`, so a factory function exported by a
  module works and its upvalue survived. The stateful `counter()` returns
  `1 2 3` across three calls, which is the case that printed *nothing at all*
  before the fix.
- **#170** — the byte sequence round-trips exactly, including `0x89` and `0xFF`
  (not valid UTF-8) and `0x1A` (end-of-file in Windows text mode). Reading the
  same file as text returns `io_error`, which is the point: text mode does not
  mangle these bytes, it refuses them, so `fs.read` was never a workaround.
- **#691** — the callback into a module runs **inside a step body**, and the step
  is recorded as `"a": "ok"` with `failed: []`. Both halves matter: the original
  defect reported no failures *and* no steps.
- **retry.until in a step body** returns `3`. That is 5.8.0's feature exercised in
  the position it did not work in when it shipped, which is the concrete thing
  #691 unblocked.

### #704, tested the way a user meets it

```
run 1: FIRST
mtime forced identical: True
run 2: SECOND
```

Write a program, run it, rewrite it, force the mtime back to what it was, run
again. Before the fix the second run printed `FIRST` — the cache key was a
function of path and clock and never of content, so any edit inside the
platform's timestamp resolution was invisible.

## One environment note, not a package defect

`nodus.exe` could not be executed from the bash shell on this machine:

```
/usr/bin/bash: .../Scripts/nodus.exe: Permission denied
```

The same machine blocked `mypy` earlier in the session with
`DLL load failed ... An Application Control policy has blocked this file`, and
mypy ran clean on retry. This is a local execution policy, not something about
the wheel: `python -m nodus` runs the identical entry point and works, and the
console script is generated by pip rather than shipped by the project.

Recorded so a future reader does not mistake it for a packaging problem — but
also **not** dismissed: it means this Stage 5 exercised the CLI through
`python -m nodus` rather than through the `nodus` shim a user actually types. The
shim's *generation* is verified by `nodus doctor`'s version-sync check passing,
which imports through the installed distribution.
