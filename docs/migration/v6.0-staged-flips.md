# Migrating to 6.0.0

**Last reviewed:** 2026-11-28, against main with all seven flips landed (sections 1-7
describe 6.0.0 behaviour; the D2 and D3 removals are still to land).
**Scope:** every behaviour 6.0.0 changes. There is nothing else in the release.

6.0.0 adds no features. Seven behaviours that warn today start failing, and
four surfaces deprecated for years are removed. That is the whole release, so
your migration is "fix what the warnings already told you about", with no new
surface to learn at the same time.

Register: `nodus/support/staged_flips.json`, checked by `nodus_gate --flips`.
Reasoning and gate conditions: `docs/governance/V6_0_PLAN.md`.

## Start here

On 5.21.0, before you upgrade:

```
nodus check --staged
```

It reports what in your project breaks, without running anything: the file you
name and every project file it imports, directly or not. Six of the seven are
answerable from source. One is not, and the report says so per flip rather than
implying a clean bill of health:

```
nothing found in the 6 flip(s) checked; 1 could not be checked from source
```

Before 5.21.0 it scanned only the file you named, although it said it checked
what that file imports (#1022). Re-run it if you relied on an earlier answer.

**A clean run is not "ready".** Record equality (#545) depends on the runtime
type of both operands, so nothing static can find it.

For that one, collect what a run hits:

```
NODUS_STAGED_FLIP_REPORT=.nodus/staged.jsonl nodus test
NODUS_STAGED_FLIP_REPORT=.nodus/staged.jsonl nodus check --staged
```

Every staged-flip warning appends a record to that file, so a whole test suite
leaves an exposure list instead of stderr that scrolled past. The second command
then reports #545 as **checked, by a run** rather than as unchecked. Unset, it
records nothing and costs nothing.

The report covers the paths that ran, which is why it complements the static
scan rather than replacing it: source coverage for six flips, path coverage for
the seventh.

On 6.0.0, the scans for the flips that changed a program's behaviour run under
plain `nodus check`: an error where the scan is exact, a warning where the run
decides. `nodus check --staged` has nothing left to report, since every flip
has landed.

Everything below is also warned about at runtime, on the path you actually run,
as of 5.11.0. If you have been ignoring a warning, this is the list of what it
was about.

## 1. The default workflow store is SQLite (#174, #797)

**This is the only one that can cost you data, and the only one to deal with
before you upgrade rather than after.** The others break a build: loud,
immediate, fixable in place. This one is about run state you already have.

In 5.x, with nothing configured, workflow runs were recorded in the file-backed
JSON store (`.nodus/workflow_framework/runs/`). In 6.0.0 they are recorded in
SQLite, in `.nodus/workflow_framework.sqlite3` beside it. Runs in the JSON store
are **not visible** to a SQLite one, so an in-flight `waiting` run does not move
when the default changes.

### What 6.0.0 does about runs it cannot see

It refuses rather than switching silently. With no backend configured, if the
JSON store holds runs the SQLite store does not, anything that opens the default
store stops (`nodus run` on a program that runs a workflow, `nodus workflow`,
`nodus serve`, an embedded `run_workflow()`), naming the runs and what to type:

```
Error: the default workflow store is SQLite (.nodus/workflow_framework.sqlite3),
and 1 run record(s) in the file-backed JSON store at .nodus/workflow_framework
are not in it, so they would be invisible to every `nodus workflow` command and
a parked run among them could not be resumed: g_fff938ca. Copy them with
`nodus workflow migrate-store --to sqlite` (non-destructive; supports --dry-run),
or set NODUS_WORKFLOW_STORE_BACKEND=local to keep the JSON store. Runs you do not
want can be deleted from .nodus/workflow_framework/runs.
```

(Paths shortened; the real message prints them absolute.) The failure this
staging existed to prevent, a parked run that quietly stops existing, cannot
happen. A project with no runs sees nothing at all.

### Do you have anything at risk?

On 5.21.0, `nodus check --staged` reports the count. Or look directly:

```
ls .nodus/workflow_framework/runs
```

No runs means nothing to do.

### If you want to keep the JSON store

Say so:

```
NODUS_WORKFLOW_STORE_BACKEND=local
```

That stays supported. It is a host stating intent, not an oversight, and the
flip only changes what happens when *nothing* was chosen.

### Otherwise, migrate

Before or after upgrading; on 6.0.0 the refusal tells you to, and
`migrate-store` is the one command it does not stop:

```
nodus workflow migrate-store --to sqlite --dry-run
nodus workflow migrate-store --to sqlite
```

Verified on 5.11.0 against a workflow parked at `workflow_wait`:

| | |
|---|---|
| `--dry-run` reports | `migrated_count: 1`, `waiting_count: 1`, `waiting_migrated: ["g_94ce0b5c"]` |
| after the real run | the JSON store still holds its record — **the copy is non-destructive** |
| the parked run, under SQLite | still `waiting`, and still resumable |

On 6.0.0, `--to sqlite` copies from the JSON store into the SQLite file the
runtime will open, including when `NODUS_WORKFLOW_STORE_ROOT` moved the JSON
store: the SQLite file then sits beside it, as `<that root>.sqlite3`.

Two things worth knowing before you run it:

- **`--dry-run` creates the target database file.** It is empty (schema only,
  zero rows, nothing copied), but it does appear.
- **The JSON store is left intact.** Migrating copies; it does not move. A run
  present in both is not refused, so keeping the old store as a backup is fine.
  Remove it once you have confirmed the runs you care about are resumable.

### If you had already chosen SQLite

`NODUS_WORKFLOW_STORE_BACKEND=sqlite` keeps its 5.x meaning: the same file, and
`NODUS_WORKFLOW_STORE_PATH` still moves it. If the JSON store holds runs SQLite
lacks, you are warned once, naming them, and not stopped, because you chose the
switch yourself.

## 2. A concurrent write that loses an update becomes an error (#547)

Two steps the graph does not order, both writing one `state` cell, where they
disagree or one read the cell before writing it. In 5.x that warned and the last
write won. In 6.0.0 the run fails (path shortened):

```
Workflow_error error at r.nd:7:21: steps a and b both wrote state 'counter' while running concurrently and each read it before writing, so one update was lost; only b's write would survive. Declare `with { merge: "sum" }` (or "append") to combine them, or `merge: "any"` if you meant last-write-wins.
```

`nodus check` finds these **without running the workflow**, as warnings, and
finds more than the runtime does: it reports every pair that could race on some
interleaving, where the runtime refuses the pair that raced on the one that
happened. On 5.21.0, `nodus check --staged` reported them.

### The fix is to say what you meant

If the branches are contributing to a total, fold them:

```nodus-expect=output
workflow tally {
    state total = 0i with { merge: "sum" }

    step north {
        total += 3i
        return "north"
    }
    step south {
        total += 4i
        return "south"
    }
}

fn main() {
    let r = run_workflow(tally)
    print("total: \(r["state"]["total"])")
}
```

Output:

```
total: 7
```

`"append"` collects into a list; `"union"` deduplicates. If you genuinely meant
last-write-wins — the branches agree, or you do not care which lands — declare
that instead, and the cell stops warning:

```
state cursor = 0i with { merge: "any" }
```

If the two steps should not run concurrently at all, order them: `step b after
a`, or declare the cell `with { barrier: true }` and let every reader wait for
every writer.

**A cell nothing else writes is unaffected**, and so is a pair the graph already
orders. This only fires on a genuine race.

## 3. An unrecognised type name becomes an error (#609)

In 5.x, `fn greet(name: strng)` was ignored: the annotation was silently
dropped, so nothing on it was checked, forever. From 5.11.0 both `nodus check`
and `nodus run` warned:

```
warning: Unknown type name 'strng' — did you mean 'string'? It is currently
ignored, so nothing on this annotation is checked; in 6.0.0 it becomes an error.
Known types: any, bool, float, function, int, list, map, nil, record, string.
```

In 6.0.0 it is a syntax error at the annotation, from `nodus run`, `nodus check`
and the editor alike (path shortened):

```
Syntax error at typo.nd:2:16: Unknown type name 'strng' -- did you mean 'string'? Known types: any, bool, float, function, int, list, map, nil, record, string.
```

Imported modules are refused on the same terms, at their own path.

The fix is the spelling. The known set is `any`, `bool`, `float`, `function`,
`int`, `list`, `map`, `nil`, `record`, `string` — `map` and `record` became
spellable in 5.6.0, so an annotation you could not write before may be writable
now.

## 4. A `worker:` declaration with no dispatcher becomes an error (#798)

`step a with { worker: "gpu" }` says *run this somewhere else*. In 5.x, with no
dispatcher registered, it ran in this process with no isolation and reported
success, the opposite of what the declaration asked for. In 6.0.0 the workflow
is refused before any step runs:

```
Workflow_error error at w.nd:8:13: a step declares worker 'hardened-sandbox', but no worker dispatcher is registered, so it cannot run with the isolation it asked for. Run under `nodus serve` with a registered worker, pass `worker_dispatcher=` to NodusRuntime, or remove the declaration to run in-process.
```

Either register a dispatcher — run under `nodus serve` with a registered worker,
or pass `worker_dispatcher=` to `NodusRuntime` — or remove the declaration if
in-process is what you actually want.

`nodus check` warns about every `worker:` declaration in your project (on 5.21.0,
`nodus check --staged` listed them). It does not try to guess whether you will
have a dispatcher at run time, because that is a deployment fact: if you
register one, the warning is a note you can ignore.

## 5. Record `==` is structural (#545)

In 5.x two records compared by **identity**: `record {x: 1i} == record {x: 1i}`
was `false`, while the equivalent map was `true`. In 6.0.0 records compare by
kind and field by field, like every other value, and that comparison is `true`:

```nodus-expect=output
fn main() {
    let a = record {x: 1i}
    let b = record {x: 1i}
    print("equal: \(a == b)")
    print("the same record: \(a == a)")
}
```

Output:

```
equal: true
the same record: true
```

The change only turns `false` into `true`, for two distinct records with equal
fields, and the same for a map or list that holds them. If you used `==` as an
identity test, to tell equal-valued records apart, compare a field that is
unique to each record instead.

Nothing static can find such a comparison, since it depends on the runtime type
of both operands. On 5.21.0, run your program or tests under
`NODUS_STAGED_FLIP_REPORT` (see *Start here*): a one-time warning fires exactly
when a comparison's answer will change, and the report collects it.

Unchanged: `datetime` still compares by instant and `duration` by length, a
function-valued field compares by identity, and a record never equals a map.
`merge: "union"` now accepts records, which it refused in 5.x because it could
not deduplicate them.

## 6. A rebuild that re-runs a top-level effect refuses it (#917)

When a stored run is resumed (a workflow resume, `nodus workflow sweep`, a
durable coroutine picked up after a crash), its program is rebuilt by re-running
the source stored with the run. That re-run exists to re-bind definitions. It
already skips `fn main()` and the scheduling builtins (`spawn`, `spawn_after`,
`run_loop`, `wait`). But any other call at the top level that reaches outside the
program used to happen again on every resume:

- a builtin with a write or remote capability: a file write, an HTTP request
  (GET included), a subprocess, `env_set`, an agent or tool call, a memory write;
- a host function, unless it was registered `rebuild_safe=True`.

In 5.x each one was reported as it happened:

```
a rebuild re-ran builtin `write_file` at <memory>:1:1, which reaches outside the program, so it happened again. In 6.0.0 this is refused; move the call into `fn main()`, which a rebuild skips (#917).
```

In 6.0.0 the rebuild refuses it instead, and the resume fails with that call
named:

```
re-executing the module to rebuild 'test' failed: LangRuntimeError: a rebuild re-ran builtin `write_file` at <memory>:1:1, which reaches outside the program, and rebuild effects are refused. To resume a run whose stored source does this, set NODUS_REBUILD_EFFECTS=allow (or pass rebuild_effects="allow"); to stop doing it, move the call into `fn main()`, which a rebuild skips.
```

The run is left as it was, so it can still be resumed once the effect is
allowed. Reads are not affected: `read_file`, `env_get` and memory reads can sit at
the top level.

**To fix a program now**, move the work into `fn main()`. A config read through
your own host function can stay at the top level if you register it
`register_function("load_config", fn, rebuild_safe=True)`.

**Runs stored before the fix** still carry the old source, because a resume
rebuilds from the stored copy, so fixing the program does not reach them. Resume
those with the effect allowed. **`NODUS_REBUILD_EFFECTS=allow`** in the resuming
process works on every path: `nodus workflow resume`, `deliver`,
`resume_workflow()`, `nodus serve` and the sweep. A run waiting on an event can
only go through one of the first three, since a sweep does not resume it. A mode
passed directly, `runtime.sweep(rebuild_effects="allow")` or
`nodus workflow sweep --rebuild-effects allow`, wins over the variable.
`rebuild_effects="warn"` keeps the 5.x behaviour of running the effect and
reporting it.

`nodus check` finds these from source (#922), as warnings, since a program that
is never resumed runs correctly. Until 6.0.0, `nodus check --staged` reported
them. It looks in any file
that runs a workflow, a goal or a durable coroutine: at its top-level statements
outside `main`, and in the functions those call. It reports effectful builtins,
stdlib wrappers such as `fs.write`, and host functions declared with `extern`.
A host function called *without* an `extern` declaration can only be seen when
it runs. Resume or sweep with `NODUS_STAGED_FLIP_REPORT=<path>` set and re-run
`check --staged`, and those are added to the same flip's findings.

## 7. `run_loop()` called from a library becomes an error (#1021)

`run_loop()` runs every coroutine in the scheduler's queue until the queue is
empty, and there is one queue for the whole program. Called from a module the
program imports, it runs the coroutines the *caller* had spawned and not yet
started, at a moment the caller did not choose. Two files, side by side:

```text
// lib.nd
export fn fetch_all() {
    run_loop()
}

// main.nd
import "./lib.nd" as lib
spawn(coroutine(fn() { print("caller's own work") }))
print("before")
lib.fetch_all()
print("after")
```

`nodus run main.nd` on 5.21.0, with the warning's absolute path shortened to
`lib.nd`:

```
before
warning: run_loop() was called from library code at lib.nd:2:5. It runs every coroutine its caller has spawned, not only the library's own. In 6.0.0 this is an error; return the task for the caller to drive, or call wait(task), which stops when that task settles (#1021).
caller's own work
after
```

The caller's coroutine ran inside `lib.fetch_all()`, which is the defect. In
6.0.0 the call is refused, before it runs anything (paths shortened):

```
before
Runtime error at lib.nd:2:5: run_loop() was called from library code at lib.nd:2:5. It runs every coroutine its caller has spawned, not only the library's own, so only the program's entry file may call it (#1021, since 6.0.0). Return the task for the caller to drive, or call wait(task), which stops when that task settles.
Stack trace:
  at fetch_all (lib.nd:2:5)
```

Called inside a spawned coroutine, the refusal fails that coroutine and is
reported, as any error a spawned task raises is; the program carries on.

"Library code" means any module but the program's entry file: a module
function, called inside a coroutine or not, and an imported module's own top
level. **`run_loop()` in the entry file is unchanged**, in a function or a
coroutine included, and so is a closure the program hands to a library, which is
still the program's code when the library calls it.

`nodus check` reports each `run_loop()` call in a file your program imports as an
**error**, and exits 1. It is the one landed flip whose check is an error, because
the scan is exact: every call it finds is refused whenever it runs.

**To fix a library now**, return the task and let the caller drive it, or wait
for what it needs:

```nd
import "std:http" as http

export fn fetch(url) {
    let t = spawn(coroutine(fn() { return http.get(url) }))
    return wait(t)       // stops when t settles; raises its failure into you
}
```

`wait(t)` still runs other queued coroutines while it waits, since `t` may need
them. What changes is when it stops: as soon as `t` settles, not when the queue
is empty.

`std:async.parallel` and `series` used to call `run_loop()` themselves. They
stopped in 5.21.0, and their contract is unchanged: they return nil, a failing
task is reported as before, and the other tasks still run. The difference is
that the caller's unrelated coroutines are no longer guaranteed to have finished
when they return.

On 5.21.0, `nodus check --staged` lists every `run_loop()` call in the files your
program imports, with its line, and the runtime warning fires for exactly those
calls, so you can fix them before upgrading.

## Surfaces removed (D2, D3)

Deprecated with warnings for years, and removed because a major is the only
release that can:

- **`.tl` source files.** Rename them to `.nd`. Running one prints
  `Warning: legacy .tl file detected. Consider using .nd.`
- **`language.py` and `language.bat`**, the legacy launchers in the source
  repository. Use the `nodus` command.
- **`nodus.tooling.tiny_vm_lang_functions`**, a shim that re-exports the
  package. Import from `nodus` directly.
- **`NodusRuntime._last_vm`**, which warns `use get_execution_stats() instead`
  on every read. `active_vm()` is the public way to reach the last run's VM.

## What is *not* changing

Worth stating, because a major invites the assumption that everything moved:

- **The bytecode format.** `BYTECODE_VERSION` stays at 5, where 5.17.0 moved it,
  and the 52-opcode set is untouched. Cached bytecode is keyed on the version,
  so it recompiles once, as after any release.
- **`nodus run`'s capability defaults.** The deny-by-default change was 5.0.0
  (`docs/migration/v5.0-deny-by-default.md`), and `nodus run` was deliberately
  not part of it.
- **Companion packages.** Every published first-party companion carries a `>=`
  floor with no upper cap, so installing 6.0.0 alongside the ecosystem resolves.
  That is a deliberate policy, adopted after five of six companions capping
  `<5.0.0` made 5.0.0 unadoptable.
