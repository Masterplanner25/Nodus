# Upgrading from Nodus v4.0.x to v4.1.x

**There are no breaking changes.** v4.1.0 and v4.1.1 are backward-compatible
with v4.0.x: no bytecode break, no removed APIs, no changed defaults. Code that
runs on 4.0.8 runs unchanged on 4.1.1.

```bash
pip install --upgrade nodus-lang
nodus --version   # Nodus 4.1.1
```

If you are migrating from v3.x, start with [v3-to-v4.md](./v3-to-v4.md). For
changes within the v4.0 patch series, see
[v4.0-patch-notes.md](./v4.0-patch-notes.md).

---

## v4.1.0 — new syntax (additive)

The first new language syntax since v4.0. Nothing you already wrote needs to
change; these are new options.

### `match` expressions (#308)

```nd
fn classify(code) {
    return match code {
        200i => "ok",
        404i => "not found",
        _ => "unknown",
    }
}
print(classify(404i))
```

Output:

```
not found
```

`match` is an **expression**, so it works as a `let` right-hand side, a `return`
value, a call argument, or nested inside another `match`. Arms compare with
`==`, the first match wins, and `_` is the catch-all and must be last. A
scrutinee that matches no arm with no `_` present raises at runtime.

**Value matching only** — there is no destructuring or binding of matched
parts. That is why the surface is Mostly Stable rather than Stable: adding
binding patterns later would extend it.

Replaces stacked `if`/`else if` chains wherever every branch tests the same
value against constants.

### `break` and `continue` (#309)

```nd
for n in [1, 2, 3, 4, 5] {
    if (n == 2) { continue }
    if (n == 4) { break }
    print(n)
}
```

Output:

```
1.0
3.0
```

Both work in every loop form — `while`, C-style `for`, and `for … in`. In a
C-style `for`, `continue` still runs the increment clause, matching C
semantics.

Two compile-time errors to know:

- Outside any loop: `'break' outside a loop`.
- Jumping out across a `try`/`catch`/`finally` boundary: `'break' cannot cross
  a try/catch/finally boundary`. A loop entirely *inside* a `try` is fine — it
  is escaping the handler that is rejected, because that would strand the
  runtime's exception-handler stack.

**If you wrote flag-variable workarounds**, they still work. You can now
replace them, but nothing forces you to.

### Also in 4.1.0

- `agent.call_async` / `agent_call_async`, so agent fan-out overlaps instead of
  serializing (#294).
- Workflow/goal `after` cycles are rejected when the graph is built;
  `run_workflow()` returns an err record with `kind = "workflow_error"` (#323).
- Workflow resume no longer re-executes the workflow or clobbers the caller's
  VM (#322, #328).

## v4.1.1 — a fix that may make dormant code start working

### Closures passed to a module function inside a container (#339)

This is the one upgrade note worth reading carefully, because the fix **changes
runtime behavior of code you already have** — in your favour, but noticeably.

Before 4.1.1, a closure nested inside a **list, map, or record** handed to a
module function executed against the wrong bytecode. Under the CLI that raised
`Stack underflow`; under `NodusRuntime` it was worse — the task body silently
never ran and `ok` was still `True`.

```nd
// helper.nd
export fn run_all(fns) {
    let out = ""
    let i = 0
    while (i < len(fns)) {
        out = out + fns[i]()
        i = i + 1
    }
    return out
}
```

```nd
import "./helper" as h
print(h.run_all([fn() { return "a" }, fn() { return "b" }]))
```

Output on 4.1.1:

```
ab
```

On 4.0.x the same program raised `Stack underflow` under the CLI, or printed an
empty string under `NodusRuntime`.

**What to check when you upgrade:**

- If you worked around this by **inlining** a loop that a library was supposed
  to run, that workaround is no longer necessary. It will keep working; you can
  remove it at your convenience.
- If you have code whose callbacks silently never ran under `NodusRuntime`,
  **they will now execute.** Side effects those callbacks perform — writes,
  network calls, counter increments — start happening. This is the intended
  behavior, but it is a real change in what your program does.
- This affected **every** `.nd` library taking callbacks in a container, not
  just the standard library.

### `std:async` — partially fixed

`async.parallel` and `async.series` now run their tasks, including with
pre-built coroutines and with tasks that `sleep()` (a sleeping task suspends and
the others continue).

**`async.worker_pool` and `async.pipeline` are still non-functional** —
[#339](https://github.com/Masterplanner25/Nodus/issues/339) remains open for
them. They spawn onto the module's own scheduler, which nothing drives, so work
is silently dropped. Use the `coroutine()` / `spawn()` / `run_loop()` built-ins
directly, as documented in
[standard-library.md §11](../guide/standard-library.md).

## Editor support lag

Neither the in-repo grammar nor the published `nodus-vscode` v0.1.0 extension
highlights `match`, `break`, or `continue` yet
([#357](https://github.com/Masterplanner25/Nodus/issues/357)). The code is valid
and runs; it just renders as plain text until the extension is republished.
