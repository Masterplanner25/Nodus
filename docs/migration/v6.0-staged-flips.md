# Migrating to 6.0.0

**Last reviewed:** 2026-09-06, against 5.11.0.
**Scope:** every behaviour 6.0.0 changes. There is nothing else in the release.

6.0.0 is **flip-only**. It adds no features. Five behaviours that warn today
start failing, and that is the whole release — so your migration is "fix what
the warnings already told you about", with no new surface to learn at the same
time.

Register: `nodus/support/staged_flips.json`, checked by `nodus_gate --flips`.
Reasoning and gate conditions: `docs/governance/V6_0_PLAN.md`.

## Start here

```
nodus check --staged
```

It reports what in your project breaks, without running anything. Four of the
five are answerable from source; the fifth is not, and the report says so per
flip rather than implying a clean bill of health:

```
nothing found in the 4 flip(s) checked; 1 could not be checked from source
```

**A clean run is not "ready".** Record equality (#545) depends on the runtime
type of both operands, so nothing static can find it.

For that one, collect what a run hits:

```
NODUS_STAGED_FLIP_REPORT=.nodus/staged.jsonl nodus test
NODUS_STAGED_FLIP_REPORT=.nodus/staged.jsonl nodus check --staged
```

Every staged-flip warning appends a record to that file, so a whole test suite
leaves an exposure list instead of stderr that scrolled past. The second command
then reports #545 as **checked, by a run** rather than as unchecked. Unset, it
records nothing and costs nothing.

The report covers the paths that ran, which is why it complements the static
scan rather than replacing it: source coverage for four flips, path coverage for
the fifth.

Everything below is also warned about at runtime, on the path you actually run,
as of 5.11.0. If you have been ignoring a warning, this is the list of what it
was about.

---

## 1. The default workflow store becomes SQLite (#174, #797)

**This is the only one that can cost you data, and the only one that needs doing
before you upgrade rather than after.** The other four break a build: loud,
immediate, fixable in place. This one silently strands a parked run.

Runs recorded in the file-backed JSON store are **not visible** to a SQLite
store. An in-flight `waiting` run does not move when the default changes — it
becomes unresumable.

### Do you have anything at risk?

```
nodus check --staged
```

reports the count, or look directly:

```
ls .nodus/workflow_framework/runs
```

No runs means nothing to do. The default changing is invisible to a project with
no state.

### If you want to keep the JSON store

Say so, and the warning stops:

```
NODUS_WORKFLOW_STORE_BACKEND=local
```

That stays supported at 6.0.0 and after. It is a host stating intent, not an
oversight, and the flip only changes what happens when *nothing* was chosen.

### Otherwise, migrate before upgrading

```
nodus workflow migrate-store --to sqlite --dry-run
nodus workflow migrate-store --to sqlite
```

Verified on 5.11.0 against a workflow parked at `workflow_wait`:

| | |
|---|---|
| `--dry-run` reports | `migrated_count: 1`, `waiting_count: 1`, `waiting_migrated: ["g_94ce0b5c"]` |
| after the real run | the JSON store still holds its record — **the copy is non-destructive** |
| the parked run, under SQLite | still `waiting`, and still resumable |

Two things worth knowing before you run it:

- **`--dry-run` creates the target database file.** It is empty — schema only,
  zero rows, nothing copied — but it does appear, which surprises people who
  expect a dry run to touch nothing.
- **The JSON store is left intact.** Migrating copies; it does not move. Keep
  the old store until you have confirmed the runs you care about are resumable,
  then remove it if you want to.

## 2. A concurrent write that loses an update becomes an error (#547)

Two steps the graph does not order, both writing one `state` cell, where they
disagree or one read the cell before writing it. Today that warns and the last
write wins. At 6.0.0 it is an error.

`nodus check --staged` finds these **without running the workflow**, and finds
more than the runtime warning does: it reports every pair that could race on
some interleaving, where the warning reports the pair that raced on the one that
happened.

### The fix is to say what you meant

If the branches are contributing to a total, fold them:

```nodus-expect=output
workflow tally {
    state total = 0i with { merge: "sum" }

    step north {
        total += 3i
        return "north"
    }
    step south {
        total += 4i
        return "south"
    }
}

fn main() {
    let r = run_workflow(tally)
    print("total: \(r["state"]["total"])")
}
```

Output:

```
total: 7
```

`"append"` collects into a list; `"union"` deduplicates. If you genuinely meant
last-write-wins — the branches agree, or you do not care which lands — declare
that instead, and the cell stops warning:

```
state cursor = 0i with { merge: "any" }
```

If the two steps should not run concurrently at all, order them: `step b after
a`, or declare the cell `with { barrier: true }` and let every reader wait for
every writer.

**A cell nothing else writes is unaffected**, and so is a pair the graph already
orders. This only fires on a genuine race.

## 3. An unrecognised type name becomes an error (#609)

`let x: strng = "hi"` is ignored today: the annotation is silently dropped, so
nothing on it is checked, forever. At 6.0.0 it is an error.

Both `nodus check` and `nodus run` report these as of 5.11.0, naming the near
miss:

```
warning: Unknown type name 'strng' — did you mean 'string'? It is currently
ignored, so nothing on this annotation is checked; in 6.0.0 it becomes an error.
Known types: any, bool, float, function, int, list, map, nil, record, string.
```

The fix is the spelling. The known set is `any`, `bool`, `float`, `function`,
`int`, `list`, `map`, `nil`, `record`, `string` — `map` and `record` became
spellable in 5.6.0, so an annotation you could not write before may be writable
now.

## 4. A `worker:` declaration with no dispatcher becomes an error (#798)

`step a with { worker: "gpu" }` says *run this somewhere else*. With no
dispatcher registered it runs in this process with no isolation, and reports
success — the opposite of what the declaration asked for. At 6.0.0 that is an
error.

Either register a dispatcher — run under `nodus serve` with a registered worker,
or pass `worker_dispatcher=` to `NodusRuntime` — or remove the declaration if
in-process is what you actually want.

`nodus check --staged` lists every `worker:` declaration in your project. It does
not try to guess whether you will have a dispatcher at run time, because that is
a deployment fact: if you register one, the line is a note you can ignore.

## 5. Record `==` becomes structural (#545)

Today two records compare by **identity**: `record {x: 1i} == record {x: 1i}` is
`false`, while the equivalent map is `true`. At 6.0.0 records compare field by
field, like every other value, and that comparison becomes `true`.

```nodus-expect=output
fn main() {
    let a = record {x: 1i}
    let b = record {x: 1i}
    print("identity today: \(a == b)")
    print("compare a field instead: \(a.x == b.x)")
}
```

Output:

```
identity today: false
compare a field instead: true
```

**This is the one `nodus check --staged` cannot find**, because it depends on
the runtime type of both operands and annotations are optional. Run your program
or your tests under `NODUS_STAGED_FLIP_REPORT` (see *Start here*): a one-time
warning fires exactly when a comparison's answer will change — two distinct
records that field-by-field comparison calls equal — and the report collects it.

If you were relying on `==` to tell equal-valued records apart — using it as an
identity test — compare a unique field instead, as above. Nothing else changes:
`datetime` and `duration` records already compared by value and still do.

## What is *not* changing

Worth stating, because a major invites the assumption that everything moved:

- **The bytecode format.** `BYTECODE_VERSION` stays at 4. No recompilation is
  required, and the 49-opcode set is untouched.
- **`nodus run`'s capability defaults.** The deny-by-default change was 5.0.0
  (`docs/migration/v5.0-deny-by-default.md`), and `nodus run` was deliberately
  not part of it.
- **Companion packages.** Every published first-party companion carries a `>=`
  floor with no upper cap, so installing 6.0.0 alongside the ecosystem resolves.
  That is a deliberate policy, adopted after five of six companions capping
  `<5.0.0` made 5.0.0 unadoptable.

## If you find something this document does not cover

The register is the authority, not this file. `nodus_gate --flips` fails if a
behaviour in the tree promises a 6.0.0 change that is not registered, so the
list here is complete by construction as of the date at the top — but the check
that keeps it so lives in the repository, and a claim in prose is still a claim
in prose.
